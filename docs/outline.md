# 项目大纲：知识库工单处理台

状态：用户于 2026-11-11 确认六项选型；本文件定义目标与协作边界，不定义详细实现或学习排期。

## 交付主线

同一个知识库工单处理台，演进为三个独立可运行版本。业务闭环是：提交工单 → 查找知识依据 → 分类与处理 → 保存处理结果及记录。

目标按优先级排列：以真实取舍应对面试；能用 AI 工具推进具体需求；用仓库、commit、PR review 和可运行应用展示作品。三天不追求框架 API 全覆盖、论文推导或生产级系统承诺。

## 阶段差异

| 维度 | s0：传统实现 | s1：单 Agent | s2：多 Agent 与评测 |
| --- | --- | --- | --- |
| 项目完成度 | 前后端分离，工单、知识搜索、规则处理与记录形成闭环 | 同一业务由单 Agent 完成检索与工具操作 | 分工、状态管理、人工介入与阶段对照评测形成闭环 |
| Agent 技术密度 | 应用内近零，规则、关键词搜索、表单 | LangChain Agent、提示词、RAG、工具调用、基础评估 | LangGraph、子代理、上下文隔离、记忆、系统评测 |
| 人的介入程度 | 用户旁观结果与缺陷 | 用户定义成功、失败与拒答标准 | 用户与 planner 共定大纲、边界与取舍 |
| 角色分工 | 执行 Agent 接管；prompter 代拟需求，独立 reviewer 把关 | prompter、builder、reviewer 明确交接 | planner / reviewer 常规化，用户进入规划环节 |

开发仓库的五个 Agent 角色与应用内的 Agent 是两套系统；s0 可以经过独立开发审查，但应用本身仍采用传统实现。

| 阶段 | 完整应用的可见目标 | 必须尝试复现的失败 | 如何补救或保留边界 |
| --- | --- | --- | --- |
| s0 | 创建、查询与处理工单；搜索知识；保存结果；前后端一键启动 | 同义改写漏检，跨资料综合困难，规则外工单无法处理 | s1 加入语义检索、生成与工具选择 |
| s1 | 自然语言处理工单；展示引用依据和工具记录；识别部分无法回答的情况 | 检索漏掉关键资料时可能答错，长任务遗漏约束，工具失败打断流程 | s2 显式管理状态、职责、重试与人工接管 |
| s2 | 展示分工、轨迹、暂停恢复；对比同一任务集上的成功率、依据质量、耗时与成本 | 协作更慢更贵但未必更准；角色可能共享错误依据；记忆过期 | 保留单 Agent 基线、失败记录和适用范围，不预设多 Agent 优于单 Agent |

失败是待检验的预判，不是提前宣称已经发生；不故意制造功能错误。某个预判没有复现时，记录案例与实际结果，不伪造失败。

## 仓库结构目标

```text
repo/
├─ README.md                       # 当前状态与证据入口
├─ AGENTS.md                       # 执行规则、PR 门槛、CodeGraph
├─ docs/                           # 大纲、验收约定、PPT 文字大纲
├─ sources/                        # 按任务选取的资料卡，后续创建
├─ notes/
│  ├─ decisions/                   # 已批准的决策、代价与适用边界
│  └─ cases/                       # 真实经历、PR 与运行证据，后续创建
├─ .agent/
│  ├─ roles/                       # 五个角色的独立职责与输入边界
│  ├─ context-map.md               # 交接、记忆、历史访问规则
│  ├─ memory/<role>/               # 私有长期经验，本地且不入 Git
│  ├─ runs/<stage>/<pr>/<role>/    # 本轮输入清单与交付物，本地
│  └─ scratch/<role>/              # 任务后丢弃，本地
├─ .github/                        # PR 模板；检查流程随需要增加
├─ s0/                             # 独立完整应用，后续创建
│  ├─ frontend/                    # TypeScript
│  ├─ backend/                     # Python
│  ├─ scripts/                     # 启动、停止与验收入口
│  ├─ fixtures/                    # 可复现的示例工单与知识资料
│  ├─ evidence/                    # 实际成功、失败、评估记录
│  ├─ .env.example
│  └─ README.md
├─ s1/                             # 同样完整的骨架，加入单 Agent
└─ s2/                             # 同样完整的骨架，加入协作与评测
```

本次仅创建大纲与协作文档，树中的阶段应用和运行目录不是当前已存在的成果。s1、s2 从前一阶段演进，但各自携带依赖声明与锁定、环境模板、示例数据和启动入口，不需要先启动另一阶段。

## 技术范围

- Python 后端与 TypeScript 前端分离；具体 Web 框架、存储、模型提供商与预算待对应实施 PR 确定，本次不擅自增加选型。
- s1 使用 LangChain Agent 接口；LCEL 只在具体链路需要时使用，不另设 API 记忆章节。
- s2 以 LangGraph 支持状态与协作；保留单 Agent 对照，评测不只依赖模型自评分。
- Skill 来自实际重复工作；扩展重点为 MCP 接入与部署复现。微调只形成是否值得做的决策记录，不训练模型。
- 唯一运行模式为真实模型调用；演示数据可以固定，但不把 mock 回答或历史回放当作真实 Agent 结果。调用失败明确报告，不静默切换模拟模式。

## 交付验收

| 检查项 | 需要留下的证据 |
| --- | --- |
| PR 列表能解释阶段收获与取舍 | 标题写明行为变化及剩余边界，正文链接决策与 review |
| 任一阶段可独立启动 | 从干净检出按 README 操作的记录；依赖声明、环境模板、启动脚本齐全 |
| 3 分钟启动目标 | README 明示机器、网络、运行时和有效 API 凭证等前置条件；在此前置下记录 clone 后到可用的耗时，依赖安装时间计入，不预先宣称通过 |
| Agent 调用真实可验证 | s1/s2 留下真实请求执行证据和失败报告，隐去凭证；s0 不需模型凭证 |
| 上下文边界有据可查 | 独立会话、实际输入文件清单、按角色隔离的记忆路径 |
| 失败预判接受检验 | 每阶段至少保留一个边界案例及实际结果，说明修复或接受的限制 |
| 评测具备比较条件 | 固定任务集与版本，记录配置、结果、耗时和成本口径，保留 s1 基线 |
| 审查对应真实提交 | GitHub commit comment 指向受审 SHA，最终通过结论对应当前 HEAD |

目前没有应用、实测耗时和效果数据；以上均为后续交付门槛。若三分钟目标未达成，记录失败并修复或交用户调整标准，不能自行删减验收。

## PR 与笔记

分支 → PR → 独立 reviewer 的 commit comment → 修正与复核 → 检查 → 按已授权边界合并。根目录大纲和笔记走相同流程；具体边界见 [上下文地图](../.agent/context-map.md)。

标题示例：`[s1] 加入 RAG 与工具调用；保留漏检反例`。阶段可以包含多个 PR。笔记由 Agent 生成，采用“决策 / 一句话结论 / 证据或可运行代码”，用户只删改、批注。
